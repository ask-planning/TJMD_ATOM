# ATOM_取込結果確認画面 設計書

## 1. 画面概要

| 項目 | 内容 |
|---|---|
| 画面名 | 取込結果確認画面 |
| 画面ID（仮） | ATOM_取込結果確認 |
| 旧Accessフォーム | `F_1_取込内容確認_MAIN` |
| 遷移元 | **INVOICE取込画面** |
| 目的 | INVOICE取込処理で取り込んだデータの内容を一覧表示し、INVOICE／PACKINGの取込結果を確認する |
| 画面形式 | Web画面 |
| 主な機能 | INVOICE No.選択、取込結果一覧表示、INVOICE/PACKING表示切替、EXCEL画面遷移、閉じる |

---

## 2. 画面レイアウト

画面構成は現行Access画面を基本とし、Web画面向けに再構成する。

### 2.1 ヘッダー部

画面上部に以下を表示する。

| 項目 | 内容 |
|---|---|
| 画面タイトル | **テキストデータ取込結果** |
| 参照ユーザー | 現行画面に表示されている参照ユーザー情報。既存仕様を踏襲する |
| 閉じるボタン | 画面右上に配置 |

## 3. 検索・選択条件部

### 3.1 元INV_NO

| 項目 | 内容 |
|---|---|
| 画面表示名 | 元INV_NO |
| UI | プルダウン |
| 必須 | 任意 |
| 内容 | 確認対象となるINVOICE No.を選択する |
| 選択時処理 | 選択されたINVOICE No.に紐づく取込結果を一覧に表示する |

## 4. 表示切替部

画面右上にINVOICE／PACKINGの表示切替機能を設ける。

### 4.1 PACKING / INVOICE切替ボタン

現行Accessでは1つのボタンのCaptionを変更しているが、Web版では現在の表示対象が分かりやすいUIとする。

初期表示は **INVOICE** とする。

#### INVOICE表示中

一覧にはINVOICEデータを表示する。

切替操作を行った場合、PACKINGデータへ切り替える。

#### PACKING表示中

一覧にはPACKINGデータを表示する。

切替操作を行った場合、INVOICEデータへ切り替える。

### 4.2 現行Access処理

現行処理では以下のサブフォームを切り替えている。

```text
INVOICE
F_1_取込内容確認_SUB_INVOICE

PACKING
F_1_取込内容確認_SUB_PACKING
```

Web版ではサブフォームという概念は使用せず、同一一覧コンポーネントの表示データを切り替える。

## 6. PACKING表示時

PACKINGへ切り替えた場合は、現行Accessの以下の画面に相当するデータを一覧表示する。

```text
F_1_取込内容確認_SUB_PACKING
```

具体的な表示列および取得項目については、当該サブフォームのレコードソース／画面定義を確認後に確定する。

INVOICE／PACKING切替時はページ全体を再読み込みせず、一覧部分のみ再取得・再描画する。

## 7. ボタン仕様

### 7.1 EXCELへ

| 項目 | 内容 |
|---|---|
| 表示名 | EXCELへ |
| 現行コントロール | `btn_excel` |
| 処理 | メール送信画面へ遷移する |

#### 現行Access処理

```vb
If intShanghaiChotatsu = 2 Then
    intMenuNo = 201
Else
    intMenuNo = 104
End If

strInputCode = ""
intMenuNoSeq = 1

strFormName = "F_9_メール送信_MAIN"
```

その後、

```text
F_1_取込内容確認_MAIN
    ↓
F_9_メール送信_MAIN
```

へ遷移する。

### Web版仕様

以下の状態を遷移情報として保持した上でメール送信画面へ遷移する。

| 状態 | 設定値 |
|---|---|
| 上海調達区分 = 2 | MenuNo = 201 |
| 上記以外 | MenuNo = 104 |
| InputCode | 空文字 |
| MenuNoSeq | 1 |
| 戻り先 | 取込結果確認画面 |

Accessのグローバル変数は使用せず、Web版ではセッション等の画面間状態管理に置き換える。

※ボタン名は現行踏襲で「EXCELへ」とするが、実処理はメール送信画面への遷移となっているため、必要に応じて名称変更を検討する。

## 8. 閉じる処理

### 8.1 閉じるボタン

| 項目 | 内容 |
|---|---|
| 表示名 | 閉じる |
| 現行コントロール | `btn_tojiru` |
| 処理 | 遷移元画面へ戻る |

本画面の基本遷移元は **INVOICE取込画面** とする。

Web版では原則として以下の遷移とする。

```text
INVOICE取込画面
      ↓
取込結果確認画面
      ↓
   ［閉じる］
      ↓
INVOICE取込画面
```

### 8.2 戻り値

閉じる際、必要に応じて以下の値を遷移元へ引き継ぐ。

| 項目 | 現行名称 |
|---|---|
| INVOICE No. | `pk_invoice_no_main` |
| REF No. | `REF_NO` |
| テキスト名称 | `text_name` |
| 通貨種別 | `currency_type` |

INVOICE No.が未設定の場合は未選択状態として扱う。

### 8.3 現行Accessの例外処理

現行Accessでは`return_form_name`によって戻り先を変更している。

```text
return_form_name = NULL
→ F_1_上海輸入_INVOICE取込

return_form_name = F_9_メール送信_MAIN
→ F_1_R3購買発注取込

その他
→ return_form_name指定画面
```

Web版については、本画面の通常遷移元をINVOICE取込画面とする。

メール送信画面等から本画面へ戻る導線を今後残す場合は、`returnUrl`または画面遷移情報をセッションに保持し、戻り先を制御する。

## 9. 再接続処理

現行Accessには以下の処理が存在する。

```vb
Private Sub btn_setsuzoku_Click()

    '再接続
    Call Login_ReInput("F_1_取込内容確認_MAIN")

End Sub
```

画面上では接続／再ログイン用アイコンとして配置されている。

### Web版仕様

Web版ではAccess固有の「再接続」機能は設けない。

セッションが有効な場合は通常処理を継続する。

セッション切れの場合は共通セッション切れ処理を実行し、再ログイン後に本画面へ復帰できるようにする。

### 経緯

この画面を編集可能にしたが、**開き方が遷移（`Response.Redirect`）だったため編集が無駄になる**という指摘を受けた。

変更前の流れは次のとおり。

1. 取込画面（101）でエラーが出る、または「取込内容を確認」を選ぶ
2. **遷移**してこの画面が開く。＝取込画面の ViewState が破棄され、

5. ファイルを選び直して「取り込み」を押す

ただし「取り込み」と押し間違えれば消えるうえ、REF_NO の表示も失われており、
**利用者が正解の操作を知っていることに依存する**状態だった。

## 2026-08-24（不具合修正と見た目の調整）

実機で確認して見つかった 5 件を直した。

| # | 症状 | 原因 | 対応 |

| 1 | 取り込み後に**ファイルを選び直さないといけない** | ファイル選択欄はポストバックで必ず空になるブラウザの仕様 | **ファイル名だけ**をセッションで保持し、「取込済み：○○.xls」と表示する。ファイル本体は保持しない（下記参照） |
| 2 | **「閉じる」を押してもタブが消えない** | `window.close()` は**スクリプトで開いたタブしか閉じられない**。`target="_blank"` のリンクで開いていたため対象外だった | リンクの `onclick` から `AtomPage.openScreen` を呼び、`window.open` で開くようにした。開けなかったときは `target` の動作にまかせる |
| 3 | ログイン画面で **Enter を押しても進まない** | ログインボタンが `UseSubmitBehavior="false"`（押下時に無効化して二重送信を防ぐため）で、既定ボタンの指定が無かった | 入力欄を `asp:Panel` で囲み `DefaultButton="btnLogin"` を指定した |
| 4 | 確認画面の**背景色が整っていない** | — | 旧 Access の配色に寄せた。外側は薄い青、見出しは灰色、INVOICE の入力欄は白、PACKING は薄い黄色、ERR_CONTENTS は赤の太字。エラー行・警告行は行全体に色を付け、入力欄の背景を透明にして行の色が透けるようにした |
| 5 | **一覧を編集しても更新されない** | 入力欄の `TextChanged` を `RowDataBound` で結び付けていた。`RowDataBound` は**データを割り当てるときだけ**発生し、ポストバックでは呼ばれないため、イベントの受け取り先が無かった | 結び付けを `RowCreated` へ移した。`RowCreated` は ViewState から行を組み立て直すときにも発生する。行の色付け（`ApplyRowStyle`）はデータが必要なため `RowDataBound` に残した |

### #5 について（同じ間違いを繰り返さないために）

GridView のテンプレート内のコントロールに `AddHandler` するときは、必ず **`RowCreated`** を使う。

| イベント | 初回表示 | ポストバック |
|---|---|---|
| `RowCreated` | 発生する | **発生する** |
| `RowDataBound` | 発生する | 発生しない（`DataBind` したときだけ） |

ポストバックのイベントはコントロールが組み立てられた直後に発生するため、
`RowDataBound` を待っていると間に合わない。データ（`e.Row.DataItem`）が必要な処理だけを
`RowDataBound` に置く。

### #1 を見送った理由（2026-08-24 判断）

ファイル選択欄はポストバックで必ず空になるため、コントロールに値を戻すことはできない。
そこで「アップロードしたファイルをサーバーに残して再利用する」方式を一度実装したが、
**取込元フォルダに次のようなファイルが溜まる**ため取り消した。

```text
123456_20260824160142056_d7c2619f36ee4593968297014ccd902f_INV.xls
 ↑社員番号  ↑保存時刻            ↑重複防止のGUID          ↑INVOICE側
```

保存先の `Atom.UploadFolderPath` は**利用者が元ファイルを置くフォルダ**を指しているため、
残すと元ファイルと見分けがつかなくなる。解析後に必ず削除する元の動きへ戻した。

将来ファイル本体も保持する場合は、**保持用のフォルダを別に新設**してから着手する（保守マップ §8-25）。

### 代わりに入れたもの（ファイル名だけの保持）

ファイル本体は残さず、**取り込んだファイル名だけをセッションで持って表示する**。

| 項目 | 内容 |
|---|---|
| 保持するもの | ファイル名の文字列のみ（`Atom.Import.InvoiceFileName` / `Atom.Import.PackingFileName`） |
| 保持しないもの | ファイル本体、保存先のパス |
| 表示 | ファイル欄の横に「取込済み：SJ-TJ7699_INV.xls」 |
| 更新する時点 | 取り込みが成功したときだけ |
| 消える時点 | ログアウト、またはセッション切れ |

これで「何を取り込んだのか」が画面から分かる。
なお、続けてチェックと登録をやり直すだけなら「チェック→登録」で足りるため、
ファイルを選び直す必要はない。Excel を読み直すときだけ選択する。

## 2026-09-25（本登録ストアドの解析を受けた注意点）

`usp_shanghai_import_invoice_update` のソースを確認した結果（解析の本体は
`docs/specs/101_INVOICE・PACKING取込.md` の同日の節）、
**この画面の編集で壊れうる箇所が 2 つ**判明した。いずれも**未対応**で、方針の指示待ち。

### O-1　PACKING の PO を直すと 2 列が食い違う（要対応）

本登録では PO が 2 列に入る。

```text
tajima_po_no           → syanai_sansyo_no          （社内参照番号）
tajima_po_no_original  → syanai_sansyo_no_original （元の社内参照番号）
```

この画面では **PACKING の PO（`tajima_po_no`）だけが編集でき、元PO（`tajima_po_no_original`）は編集できない**。
そのため PO を直すと、本登録後に 2 列の値が食い違う。

さらに `syanai_sansyo_no` は輸入仕入実績（menuNo=107）の View が使う**突合キー**であり、
`View_kaigai_shiire_jisseki_kbn1_invoice_gokei` と `_hacchu_gokei` の結合条件に含まれる。

対応案は次の 3 つ。

| 案 | 内容 |
|---|---|
| A | **PO を編集不可にする**（突合キーは触らせない） |
| B | PO を直したら**元PO も同時に更新する**（品目コードで `R3_hinmoku_code` を同時更新しているのと同じ考え方） |
| C | 今のままにして、注意文だけ出す |

品目コードでは B を採っている（`ShanghaiImportRepository.UpdatePackingShanghaiCode`）ため、
一貫させるなら B。ただし元PO を上書きしてよいかは業務仕様の確認が必要。

### O-2　C/NO に数値でない値を入れると本登録が失敗する可能性（要確認）

ヘッダサブの箱数は**引き算**で求めている。

```sql
SUM(carton_no_to - carton_no_from + 1)
```

この画面では C/NO 開始・終了を**文字列（50桁）として編集できる**ため、
数値でない値を入れると本登録で変換エラーになりうる。

ただし `View_shanghai_packing_carton_no` の定義を確認していないため、
ビュー側で数値へ変換している可能性もある。**現時点では推測**。

確認するには下記を流す（参照のみ）。

```sql
SELECT definition FROM sys.sql_modules
WHERE object_id = OBJECT_ID(N'dbo.View_shanghai_packing_carton_no');
```

危険であれば、C/NO の入力を数値のみに制限する（`ShanghaiImportValueKind.WholeNumber` にする、
または桁数固定の書式チェックを足す）。

### O-3　MISC / FREIGHT の組み合わせを壊さないこと（注意のみ）

本登録には運賃行のための読み替えがある。

| 一時データ | 明細に入る値 |
|---|---|
| 品目コードが空＋品名が `FREIGHT` | 品目コード → `MISC` |
| 品目コードが `MISC` ＋品名が空 | 品名 → `FREIGHT` |

この画面では**品目コードと品名の両方を編集できる**ため、
片方だけ直してこの組み合わせを崩すと、運賃行が意図しない値で登録される。
現時点では画面に注意文を出しておらず、**未対応**。

### O-4　エラー行でも登録されうる（現状は実害なし）

本登録ストアドは `err_status` を見ない。PO・数量・品目コードが揃っていれば、
エラー行でも明細に入る。

現在は取込画面がエラー時に本登録へ進ませないため実害は無いが、
**この画面で値を直したあと「チェック→登録」を押す**運用では、
再チェックが走って改めて判定されるため問題ない。
