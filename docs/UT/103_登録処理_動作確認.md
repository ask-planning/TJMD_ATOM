# 103 登録処理 動作確認（最低限）

INVOICEヘッダー入力（menuNo=103）の「登 録」ボタンの確認項目。
**ここが通れば登録処理は動いている**と判断してよい、という範囲に絞っている。

仕様は `docs/specs/103_INVOICEヘッダー入力.md` §8 を正とする。

---

## 0. 始める前に（ここを外すと本番に影響する）

| # | 確認 | なぜ |
|---:|---|---|
| 0-1 | **接続先が `ATOM_dev` になっている** | `Web.config` の `AtomDb`。本番に向いたまま押すと本番データが変わる |
| 0-2 | **`Poem.UpdateEnabled` の値を確認した** | `true` だと POEM を更新する。**検証では `false` が安全** |
| 0-3 | `true` にするなら **`Poem.MakishinProcedureName` が `_dev` 版** | 本番の POEM を消す事故を防ぐ（保守マップ 74） |

> **`Poem.UpdateEnabled` が `false` のとき**、登録後のメッセージに
> 「（POEM の巻芯入出庫は更新していません。）」が付く。**これが出ていれば抑止できている。**

## 1. 入力チェック（§8.1）

押しても**登録されず**、メッセージだけ出ること。

| # | 操作 | 期待 |
|---:|---|---|
| 1-1 | 元INV_NO を未選択で「登 録」 | `INVOICE_NOを入力してください。` |
| 1-2 | 船名を空にして「登 録」 | `船名を入力してください。` |
| 1-3 | 乙仲を空にして「登 録」 | `乙仲を入力してください。` |

**B/L DATE・出荷方法・カートン数・返却パレットは空でも通る**こと（必須ではない）。

---

## 2. 新規登録（§8.2 INSERT）

**まだヘッダーが無い INVOICE** を選ぶ。

見分け方は **B/L DATE と出荷方法がグレー**になっていること。
**グレーになるのはこの 2 つだけ**で、他の欄は登録済みでも未登録でも見た目は変わらない
（旧 Access 版に合わせている。設計書 §3.2）。

> 画面の案内文「フィールドがグレーの場合…」は旧 Access の文言のままなので、
> **全部の欄がグレーになるように読める。**文言の見直しは要検討。

| # | 操作・確認 | 期待 |
|---:|---|---|
| 2-1 | 船名・乙仲を入れて「登 録」 | `登録完了しました。` |
| 2-2 | `tbl_t_shanghai_invoice_header` を見る | **1 行増えている** |
| 2-3 | 画面が作り直される | **B/L DATE と出荷方法のグレーが外れる** |
| 2-4 | `update_login` を見る | **ログインした社員コード**が入っている |

```sql
USE ATOM_dev;
SELECT pk_invoice_no_main, ref_no, bl_date, vessel, syukka_hoho,
       carton_qty, return_pallet, otsunaka_no, update_ymd, update_login
FROM   dbo.tbl_t_shanghai_invoice_header
WHERE  pk_invoice_no_main = '（対象のINVOICE）';
```

## 3. 更新（§8.2 UPDATE）

**2 で登録した同じ INVOICE** をもう一度登録する。

| # | 操作・確認 | 期待 |
|---:|---|---|
| 3-1 | 乙仲を別の値に変えて「登 録」 | `登録完了しました。` |
| 3-2 | 上の SQL を再実行 | **行は増えず、`otsunaka_no` が変わっている** |
| 3-3 | `update_ymd` | 更新されている |

**ここで行が 2 行になったら INSERT/UPDATE の分岐が壊れている。**

## 4. 明細の反映（§8.3）

| # | 操作・確認 | 期待 |
|---:|---|---|
| 4-1 | 明細のコンテナNO・シールNO・カートン数を変えて「登 録」 | 画面を開き直しても**変更が残っている** |

## 5. 印刷用INVOICE_NO（§8.4）

**ここが一番間違えやすい。**

| # | 条件 | 期待 |
|---:|---|---|
| 5-1 | 同じコンテナNO に枝番が 2 つ以上 | 画面の「印刷用INVOICE_NO」に **`A,E` のように枝番がカンマで並ぶ** |
| 5-2 | コンテナNO が違う行 | **別々に連結される**（混ざらない） |
| 5-3 | 配送タイプが 3（日新）の行 | **連結の対象外**（§8.4 の `haiso_type <> 3`） |
| 5-4 | コンテナNO が空の行 | 何も入らない |

上の SQL の `invoice_no_print` で確認できる。

## 6. 登録後のメッセージ

| # | 条件 | 期待 |
|---:|---|---|
| 6-1 | 通常 | `登録完了しました。` |
| 6-2 | 明細に**配送予定日が 1 件でも入っている** | `（配送予定日が入力されています。外部システムへの連携は未実装です。）` が続く |

## 7. 途中で失敗したとき（トランザクション）

確認できる機会があれば見る。**無理に起こさなくてよい。**

- 登録の途中で失敗したとき、**ヘッダーだけ更新されて明細が古いまま**にならないこと
- §8 の 2〜7 は 1 つのトランザクションにまとめてある

---

## 通ったと判断する条件

**1〜6 がすべて期待どおりなら OK。**

特に落としてはいけないのは次の 3 つ。

1. **2-2 / 3-2** — INSERT と UPDATE の分岐（行が増えないこと）
2. **5-1** — 印刷用INVOICE_NO の連結
3. **0-2 / 6-3** — POEM を更新していないこと
